# Ownership and numeric migration

Production migration is deliberately an operator task. Do not run the demo seed, role grants or local database script against an existing database. Those tools guard the hostname and database name. `DATABASE_URL` is the limited application role; `DIRECT_URL` is the migration role and must not be the runtime identity. In a hosted environment, supply the privileged URL only to the migration process.

1. Take a restorable snapshot and rehearse on a copy. Check counts, foreign keys and migration history against the original schema. For a database already created with `db push`, apply the documented Prisma baseline procedure: mark `202609220001_baseline` as applied only after verifying its tables match. For an empty database, `migrate deploy` applies it normally.
2. Migration 002 moves all four original tables, including their rows, indexes and relationships, into `legacy_unowned`. Revoke schema access from every runtime or inherited role, not only PUBLIC. Our local role is created without privileges and is explicitly denied access. If an existing runtime role owns the legacy tables/schema or has elevated privileges, change to a distinct limited runtime role before starting the new app. The old application must be stopped.
3. New active tables use required owner foreign keys and `numeric(20,6)`. **No original row is assigned or copied automatically.** Original float values are retained unchanged in the archive, including malformed and nonfinite values. Migration 003 adds login limits and an explicit non-null option type check.
4. Reconcile any legacy rows only after verified owner mapping. Export original values for review; reject NaN/infinity, unsupported futures, invalid dates, nonpositive quantities and out-of-range prices. Convert valid values using PostgreSQL `round(old_value::numeric, 6)`, preserving the original archive. Record before/after amounts and owner mapping in private operational records. Half ties round away from zero. Reconcile counts and cent-level P&L before insertion. No bulk ownership-claim endpoint is exposed. The archive is the reversible copy; original binary floating-point precision cannot be recovered from a rounded numeric value alone.
5. Grant only active schema/table DML to the runtime role. Verify archive queries fail under that role. Run the integration and two-user HTTP tests before bringing the application up.

Rollback requires a maintenance window and backup. Stop writes; move the new tables into a separately restricted `multi_user_hold` schema (preserving new user data); move the four archived tables back to `public` in foreign-key-safe order, and restore the matching old application. Reconcile Prisma migration history on a restored database copy before cutover. Do not delete new rows or blindly run a destructive down migration. **The old application has no user isolation and must not be publicly exposed.** Rollback restores old float tables verbatim; it does not merge new multi-user data into them.

Checks enforce positive bounded quantity/entry, nonnegative bounded exit/stops/targets/strikes, supported sides/types/modes and close-state consistency. Options require whole contracts and contract details. SQL numeric rounding beyond six places is possible for privileged direct writes; application contracts reject that precision rather than silently rounding it. Dates are validated in the request contract. No migration is executed by the application on startup.
